**Initial suite: 5/6 (83.3%), 28 calls. Targeted follow-up: 1/1, 2 calls. Total: 30 calls**
(within the originally announced 36-call budget). The treatment case includes one failed
HTTP 503 request and a successful retry at the pending node. Available usage totals:
**53,387 input tokens, 6,823 output tokens**. Failed-request tokens are unknown; cost was not
priced because no account/token rates were supplied.

The ambiguity failure was semantic: the editor chose both matching dates, and the judge approved
the broader edit although the user had not selected a field or requested all matches. The
independent evaluation correctly failed it. The actual tool calls are retained in
`tests/fixtures/ambiguous_date_trace.json`; an offline regression proves that replaying this
approval cannot make the case score as a success.

The editor and judge prompts now explicitly distinguish knowing the old/new values from knowing
which labelled field the user intended. Choosing a block ID does not establish that intent;
the model must ask before editing unless the user identifies the scope or requests all matches.
This is a **prompt-only policy correction**, not a deterministic semantic guard. The targeted
live follow-up asked whether the visit date, review date, or both should change. It interrupted
before editing and wrote no output document.

The full six-case suite was **not** rerun after that prompt change, so this is not a claim of
6/6 under one final prompt version. One successful follow-up also does not guarantee future
model behavior. Raw per-case reports and tool results remain under the ignored run directories:
