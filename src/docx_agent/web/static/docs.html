01

Scope before code

The brief is graded on editing reliability and document integrity first. Before writing anything I fixed three numbers: how large a document may be, how fast an edit must be, and how much the whole project may spend. Each limit has a reason, and the code enforces most of them.

Document size

LevelLimitReason
Supported and tested≤ 15 pages · ≤ 300 blocks · .docx ≤ 5 MBThe whole document view fits one model call (20,000-character budget, about 5k tokens).
Degraded modeUp to ~3,000 paragraphs (~150 pages)The agent switches to find_text and range views: it still works, with more calls and cost.
Rejected> 200 MB uncompressed, > 2,000 parts, encrypted, .docRefused up front by the package layer, before any model sees the file.

Speed

Deterministic layer

Load, view, edit, check and save in under 1 second for 3,000 paragraphs. Measured at about 0.4 s for a full view and 0.4 s for validation.

One instruction, end to end

Target p50 ≤ 30 s, never more than 90 s. Planned at 3–5 model calls; a confident edit now takes 2 (see same-turn finish). Turns and retries are capped in configuration.

Budget: $2, on purpose

My remaining API credit was $2 on Claude Sonnet 5.5 ($2 per million input tokens, $10 per million output). I allocated it before the first live call:

UseRunsEstimate
First real test (catch common provider errors)3~$0.40
Deliverable samples (the three committed outputs)3–4~$0.50
Mini evaluation (five cases, one run each)5~$0.60
Reserve—~$0.50

Then I made it cheaper still: I added Gemini 3.5 Flash-Lite for its free quota, ran samples and evals on it at $0, and kept Claude Sonnet 5.5 for live verification. Both providers are wired through the same graph and checks.

Result: $1.93 of the $2 is still unspent. The whole project cost about $0.07 in Claude credit, against an allocation of $2.00; the reserve was never touched.

Safeguards: planned against shipped

  • ShippedCap the calls per run. Editor turns and review calls are bounded in settings; live evals share a hard call budget (--max-calls). SDK retries are off, so nothing retries behind the graph's back.
  • ShippedNo real API calls in tests. Every graph, CLI, menu and web test runs the real LangGraph with a scripted model.
  • ShippedAnnounce the call count before every live run. A rule in the agent instructions, and the CLI prints the cap before it starts.
  • AdaptedLog tokens and cost. Call and token counts are recorded for every sample and eval run; cost is estimated only when rates are supplied.
  • ReplacedAbort a run above $0.30. Hard call caps replaced price tracking: they bound cost for any provider, including a free one.

03

Built to survive a change of agent or provider

When the challenge started, my weekly Claude Code usage was already at 95%. Running out halfway was a real risk, so before step two I made the project portable.

Session (5 h)6%
Weekly (7 days)95%
  • Provider-neutral rules. AGENTS.md holds the working rules and integrity invariants for any coding agent; CLAUDE.md only imports it.
  • A handoff file, updated at every checkpoint. docs/HANDOFF.md lets an agent with zero context continue, and it assumes Claude-specific integrations may not carry over.
  • One gate that any agent can run. make check (lint, strict types, tests, coverage) is the same locally and in CI.

It paid off: later checkpoints were done with a different coding agent, which picked up from the handoff and ran the same gate by hand where the Claude-only hooks no longer applied.

04

Architecture decisions

Each choice serves the first grading criterion: an edit must change exactly what was asked and nothing else, and that must be checkable.

My own OPC layer, not python-docx

python-docx re-serialises every part it loaded when it saves. I read and write the zip with zipfile and lxml, parse only word/document.xml, and copy every other part unchanged. python-docx only builds test fixtures and checks outputs.

Stable block IDs

p0, t0.r1.c2.p0 for table cells, n0 for inserted paragraphs, tombstones for deleted ones. IDs live in Python, never in the XML, and never shift during a session.

Run-aware editing

A character map over the runs; boundary runs are split by cloning their formatting, so new text inherits the formatting of the text it replaces. Spans that touch images, fields or footnote references are refused with an error the model can act on.

Checks before judgment

A deterministic integrity check runs first; only then does a separate model review the result through JSON-schema structured output. A failure resets the document to the original and appends feedback; the history is never rewritten.

Two calls for a confident edit

The model may apply every edit and call finish in the same turn, saving a round trip. If any edit in that turn fails, finish is cancelled and the model sees why.

Spending bounded by construction

SDK retries are disabled, call caps live in the graph, and the model gets no shell or code execution, only typed document tools. No temperature and no forced tool_choice, which current Claude models reject.

An explicit StateGraph, not a prebuilt agent

Every route is declared, and a test pins the compiled graph's edges, so the control flow can be read and tested rather than inferred.

Load→ Agent ⇄ tools→ Validate→ Review→ Save

A question pauses the graph with interrupt() and resumes with your answer. A failed check or a rejected review resets to the original and retries, up to a cap; when the retries run out, nothing is written.

05

How integrity is proven

Five invariants, enforced by the checker on every edit and by the test suite on every push.

  1. Zip parts we did not edit keep their exact content, with the same names, order and compression.
  2. Paragraphs and tables an edit did not touch are identical as canonical XML.
  3. Inside an edited paragraph, every character outside the edit keeps its formatting.
  4. Protected content (drawings, fields, footnote references, section properties) is never removed silently.
  5. python-docx never saves agent output.
LayerWhat it proves
Round tripThe first test written: loading and saving without edits changes nothing.
Unit and corruption testsEvery tool and refusal path works, and the checker catches deliberately injected damage: changed formatting, a dropped image, an altered untouched paragraph.
Property-based (Hypothesis)Random paragraphs, run splits and formats with random edits: the text is right, outside formatting is preserved and exactly one block is touched.
Graph, CLI, menu and webThe real LangGraph with a scripted model: happy path, clarification, failed validation, rejected review, exhausted retries.
Committed samplesCI re-verifies the three real model outputs against their inputs on every push.

06

The test-and-fix loop

I chose this optional challenge because it mirrors the product: the agent's own validate, review and retry cycle is the same pattern applied at runtime.

Change→ Format + fast tests→ make check→ Review→ My commit→ CI
Live failure→ Recorded trace→ Offline regression test→ Fix→ Targeted live re-run

Early on, editor hooks ran lint and the fast tests after every edit, and a stop hook refused to let the coding agent finish while the gate was red. Those development-only hooks are not part of the deliverable; the gate and CI are.

Failures the loop caught

What went wrongHow it was fixed
A broad replacement spread bold from a date into unchanged italic text.The integrity check rejected it before saving. Edits are now token-aligned and applied atomically; a property test keeps the counterexample it found.
The model changed both of two ambiguous dates, and the reviewer approved.The independent eval failed it. The trace became a regression test, and the prompt now requires a clarifying question.
The reviewer rejected a correctly inherited bullet because it saw only text.Graph regression; the reviewer now sees the actual styles of the touched blocks.
On a macOS-written .docx, quoting an en dash as “-” retyped the document's dash.Forgiving matches now write back the document's own characters where the text is unchanged.
Sample reproducibility passed on macOS and failed in Linux CI.Pillow's font rendering differed by platform; the samples now reuse a fixed logo and a test forbids host fonts.

09

Limits I chose to state, and what's next

Out of scope today

Headers, footers, footnotes, comments and text boxes are read-only. No inserting tables or images, no changing hyperlink targets, no text spans across paragraphs. Unsupported requests get a question and an alternative, never a silent approximation. Languages: English and German are supported and tested; other Latin-script languages are untested, right-to-left and CJK are not supported.

Next

Header and footer editing; durable checkpoints so a paused edit survives a restart; repeated eval runs for a real pass rate; rendering checks in Word or LibreOffice in CI; then a hosted deployment.

Back to the editor All sample content is synthetic.

04

Architekturentscheidungen

Jede Entscheidung dient dem ersten Bewertungskriterium: Eine Bearbeitung muss genau das ändern, was verlangt wurde, und sonst nichts, und das muss prüfbar sein.

Eigene OPC-Schicht statt python-docx

python-docx serialisiert beim Speichern jeden geladenen Teil neu. Ich lese und schreibe das ZIP mit zipfile und lxml, parse nur word/document.xml und kopiere jeden anderen Teil unverändert. python-docx erzeugt nur Test-Fixtures und prüft Ausgaben.

Stabile Block-IDs

p0, t0.r1.c2.p0 für Tabellenzellen, n0 für eingefügte Absätze, Grabsteine für gelöschte. Die IDs leben in Python, nie im XML, und verschieben sich während einer Sitzung nie.

Lauf-bewusstes Bearbeiten

Eine Zeichenkarte über die Runs; Rand-Runs werden durch Klonen ihrer Formatierung geteilt, sodass neuer Text die Formatierung des ersetzten Texts erbt. Bereiche, die Bilder, Felder oder Fußnotenverweise berühren, werden mit einem Fehler abgelehnt, auf den das Modell reagieren kann.

Prüfung vor Urteil

Zuerst läuft eine deterministische Integritätsprüfung; erst dann bewertet ein separates Modell das Ergebnis über strukturierte JSON-Schema-Ausgabe. Ein Fehlschlag setzt das Dokument auf das Original zurück und hängt Feedback an; der Verlauf wird nie umgeschrieben.

Zwei Aufrufe für eine sichere Bearbeitung

Das Modell darf alle Änderungen anwenden und im selben Zug finish aufrufen; das spart eine Runde. Scheitert eine Änderung in diesem Zug, wird finish abgebrochen, und das Modell sieht den Grund.

Kosten konstruktiv begrenzt

SDK-Wiederholungen sind deaktiviert, Aufrufgrenzen liegen im Graphen, und das Modell bekommt weder Shell noch Code-Ausführung, nur typisierte Dokument-Tools. Kein temperature und kein erzwungenes tool_choice, das aktuelle Claude-Modelle ablehnen.

Ein expliziter StateGraph statt eines fertigen Agenten

Jede Route ist deklariert, und ein Test fixiert die Kanten des kompilierten Graphen: Der Kontrollfluss lässt sich lesen und testen, statt ihn zu erraten.

Laden→ Agent ⇄ Tools→ Validieren→ Review→ Speichern

Eine Rückfrage pausiert den Graphen mit interrupt() und setzt mit Ihrer Antwort fort. Eine gescheiterte Prüfung oder ein abgelehntes Review setzt auf das Original zurück und versucht es erneut, bis zu einer Grenze; sind die Versuche aufgebraucht, wird nichts geschrieben.

05

Wie Integrität belegt wird

Fünf Invarianten, durchgesetzt vom Prüfer bei jeder Bearbeitung und von der Testsuite bei jedem Push.

  1. ZIP-Teile, die wir nicht bearbeitet haben, behalten ihren exakten Inhalt, mit gleichen Namen, gleicher Reihenfolge und Kompression.
  2. Absätze und Tabellen, die eine Bearbeitung nicht berührt hat, sind als kanonisches XML identisch.
  3. In einem bearbeiteten Absatz behält jedes Zeichen außerhalb der Änderung seine Formatierung.
  4. Geschützte Inhalte (Zeichnungen, Felder, Fußnotenverweise, Abschnittseigenschaften) werden nie stillschweigend entfernt.
  5. python-docx speichert nie Agent-Ausgaben.
EbeneWas sie belegt
Round TripDer erste geschriebene Test: Laden und Speichern ohne Änderung verändert nichts.
Unit- und KorruptionstestsJedes Tool und jeder Ablehnungspfad funktioniert, und der Prüfer erkennt absichtlich eingebaute Schäden: geänderte Formatierung, ein entferntes Bild, ein veränderter unberührter Absatz.
Property-basiert (Hypothesis)Zufällige Absätze, Run-Aufteilungen und Formate mit zufälligen Änderungen: Der Text stimmt, die Formatierung außerhalb bleibt erhalten, und genau ein Block wird berührt.
Graph, CLI, Menü und WebDer echte LangGraph mit einem Skript-Modell: Normalfall, Rückfrage, gescheiterte Validierung, abgelehntes Review, aufgebrauchte Versuche.
Committete BeispieleCI prüft die drei echten Modellausgaben bei jedem Push erneut gegen ihre Eingaben.

06

Die Test-und-Fix-Schleife

Ich habe diese optionale Challenge gewählt, weil sie das Produkt spiegelt: Der eigene Validieren-Review-Wiederholen-Zyklus des Agenten ist dasselbe Muster zur Laufzeit.

Änderung→ Format + schnelle Tests→ make check→ Review→ Mein Commit→ CI
Live-Fehler→ Aufgezeichneter Trace→ Offline-Regressionstest→ Fix→ Gezielter Live-Lauf

Anfangs führten Editor-Hooks nach jeder Änderung Lint und die schnellen Tests aus, und ein Stop-Hook ließ den Coding-Agenten nicht fertig werden, solange die Schranke rot war. Diese reinen Entwicklungs-Hooks gehören nicht zur Abgabe; die Schranke und CI schon.

Was die Messungen sagen und was nicht

5/6, dann 6/6

Die erste Live-Baseline scheiterte am Mehrdeutigkeitsfall. Nach einer Prompt-Korrektur bestanden alle sechs Fälle: 35 Gemini-Aufrufe, $0. In diesem Lauf war jedes Nichtbestehen ein Anbieter-503, nie Verhalten des Agenten.

Neun unbekannte Anweisungen

Live auf Gemini und Claude Sonnet 5.5 ohne Wiederholungen: Keine gespeicherte Ausgabe verletzte die Integrität. Fehlschläge waren Ablehnungen, bei denen nichts geschrieben wurde. Die Prüfung deckte außerdem zwei deterministische Fehler und ein Prompt-Problem auf, alle mit Regressionstests behoben.

Jeder Evaluationsfall bestand einmal: ein Korrektheitsnachweis, keine gemessene Erfolgsquote. Die Live-Läufe liegen vor der Optimierung mit Abschluss im selben Zug, die durch Offline-Graph-Tests abgedeckt ist.
